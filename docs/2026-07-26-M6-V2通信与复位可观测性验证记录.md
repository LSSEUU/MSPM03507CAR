# 2026-07-26 M6 V2 通信与复位可观测性验证记录

## 范围与安全边界

本记录承接 `M6-runtime-20260726-r11`，后续主目标调整为高速直线、平滑弧线、高速陀螺仪角度控制和系统长期无复位。赛题与赛道公布前，不再为未知直角弯试验新的纯巡线失线搜索参数。

通信重构和主机工具必须持续满足以下边界：

- UART RX ISR 中单字节 `S`/空格继续立即急停，不等待协议解帧、CRC、队列或主机确认；
- 所有电机输出继续经过 `System/safety.c`，不得旁路 Safety 仲裁；
- WWDT 周期和健康窗口不放宽，不增加无条件喂狗路径；
- 周期任务不得调用 `printf`/`snprintf`/`vsnprintf`，不得阻塞等待串口；
- 高速实车按 `160→180→200→220→250 mm/s` 分级，任一级出现复位、故障、漏期、异常丢包、持续饱和或明显振荡立即回退。

## MCU reset cause 诊断边界

源码和本仓库所带 TI DriverLib 共同证明：

1. `Source/main.c` 在任何初始化前调用一次 `DL_SYSCTL_getResetCause()`；MSPM0G1x0x/G3x0x 的 `RSTCAUSE.ID` 是 read-to-clear 字段。
2. 当前代码只用 `Hardware/watchdog.c::Watchdog_WasResetCause()` 判断精确的 `DL_SYSCTL_RESET_CAUSE_SYSRST_WWDT0_VIOLATION`，命中时锁存 `SAFETY_FAULT_WATCHDOG_RESET=0x20`。
3. 原始 reset cause 随后被丢弃，既不保存也不通过 UART 上报；当前没有跨复位 breadcrumb。
4. 本次 Safety 故障为 0，因此可排除“当前这次启动由 WWDT0 复位且仍未清故障”。但 r11 无法进一步区分这次启动来自上电/BOR、长短 NRST、软件复位、调试器复位或其他系统复位，不能把其中任何一种写成已确认原因。

芯片枚举本身能够区分上电/供电异常、外部 NRST、软件 POR/BOOTRST/SYSRST/CPURST、WWDT、调试器和硬件故障。DriverLib 还提供 4 字节 `SHUTDNSTORE`，并明确这些字节在 BOR、BOOTRST 和 SYSRST 后保持且由硬件做奇偶校验；这为不写 Flash 的紧凑复位前 breadcrumb 提供了依据。真正 POR 后的 breadcrumb 不能假定有效，必须结合 reset cause 和记录标识判定。

## r12 reset diagnostics 实现

待上板固件身份推进为 `M6-runtime-20260726-r12`。本切片没有改变车辆控制参数、WWDT 周期或健康门控，主要实现如下：

- `main()` 在 `SYSCFG_DL_init()` 前只读一次 `RSTCAUSE`，立即保存 raw 值、分类和不可变启动快照；公开的 TI raw ID 均有稳定名称和 `power/external/software/watchdog/debug/hardware/bsl/unknown` 分类。raw `0x01` 命名为 `por_or_parity`，不把它误写成唯一冷上电。
- 4 字节 `SHUTDNSTORE` 使用 magic、commit、checkpoint、boot ID 低 8 位。新启动记录先使 commit 失效，写完其余字段后最后提交；正常 checkpoint 只更新阶段字节并在短临界区内完成，避免主循环与 ISR 的寄存器 RMW 互相覆盖。
- scatter 文件把 `0x20207F00`–`0x20207FFF` 划为独立 256 B `UNINIT` 区。区内两个 64 B 详细槽采用 version、length、完整 boot ID、sequence、CRC32 和最后提交标记；每个通过原调度健康门控的 20 ms 窗口先立即喂 WWDT，再记录最近喂狗时间、任务、Safety、UART/遥测 drop 与队列摘要。
- HardFault scratch 另带 magic、version、完整 boot ID、记录序号、stacked PC/LR/xPSR、CRC32 和最后提交标记，同时重建完整粗记录；请求 `SYSRST` 前后执行 `DSB/ISB`。下一启动仍以 raw 软件 SYSRST 为事实原因，并用 `hardfault` breadcrumb 表明异常来源。
- checkpoint 覆盖 5/10/20/100 ms、control RX、TX encode/submit、telemetry、grayscale、OLED、参数 Flash、WWDT service、Safety fault、ISR 急停、HardFault 和 idle。Safety checkpoint 位于 `Safety_RaiseFault()` 集中入口；ISR 急停仍先执行既有遥测停止和 Safety 制动，再用更具体的 `emergency` 覆盖 breadcrumb。
- 参数保存只在 Flash 清状态/解保护之前增加 `param_flash` checkpoint；既有无故障 IDLE/电机制动门控、A/B 选槽、CRC/commit-last、RAM writer 和 Flash 期间的特殊 WWDT 服务均未改变。真实写入中断和断电恢复仍未上板验证。
- `v`/系统报告冻结一份 reset 快照并分时输出 `RESET`、`RESETCTX`、`RESETIO`，然后输出既有 Safety/context/scheduler 行。新增三行都保留 CRLF，主机最坏长度检查低于 256 B；每 100 ms 至多输出一行，且自动 reset 报告放在 5/10/20/100 ms 周期任务之后的后台。

本切片没有完成 V2 传输层，也没有消除仓库中既有 M3/M4/M5/boot 文本诊断在 100 ms 任务内的格式化；“周期任务内无 `printf`/`snprintf`”仍是下一通信重构切片的硬验收项。当前只能确认 reset diagnostics 没有新增周期任务格式化，不能提前宣称该全局目标已经完成。

## 短按 NRST / BOOTRST 保持边界

用户确认短按板上复位键后，再次使用相同只读 identity probe 精确确认固件仍为 `M6-runtime-20260726-r12`、schema 1、revision 1、source `defaults`、generation 0。清空串口输入后发送 `v`，等待冻结快照，再发送 `c`：

```text
RESET raw=0x0C cause=external_boot class=external boot=2 checkpoint=control_rx prev_coarse=1 prev_detail=0 hardfault=0
RESETCTX prev_boot8=1 prev_boot=0 prev_cp=idle detail_cp=none seq=0 time=0 wwdt=0 hf_pc=0x00000000 hf_lr=0x00000000 hf_xpsr=0x00000000
RESETIO faults=0x00000000 miss=0 drop=0/0/0 pending=0x00 missed=0x00 state=0 q=0 health=0x00
SAFETY state=IDLE faults=0x00000000 first=0 last=0 action=0 deadline=0 pwm=0,0
CONTEXT target=0,0 speed=0,0 requested_pwm=0,0
SCHED release=6194/3097/1548/309 miss=0/0/0/0 pending=0x00
COMM tx=2448 rx=110 tx_drop=0 rx_drop=0 format=0 baud=115200 8N1
```

证据与根因边界：

- 本仓库 TI G3x0x DriverLib 将 `0x0C` 明确定义为 `<1 s` NRST 触发的 `BOOTRST_EXTERNAL_NRST`；因此本次已实际验证短按复位的 raw cause 与分类，不再把它列为未知复位类型。
- `prev_coarse=1`、`prev_boot8=1`、`prev_cp=idle` 和当前 `boot=2` 证明 4 B `SHUTDNSTORE` 的 magic/commit/boot/checkpoint 事务跨本次 BOOTRST 保持并被正确恢复。
- `prev_detail=0` 不是 `.noinit` 链接或 C 启动清零缺陷的证据。TI MSPM0 G 系列用户手册 SLAU846A 第 2.4.1.1.3 节明确说明 BOOTRST 会 power-cycle system memory，SRAM 内容丢失，而 `SHUTDNSTOREx` 不受 BOOTRST 影响；DriverLib 也只对 shutdown memory 明确承诺跨 BOR/BOOTRST/SYSRST 保持。
- scatter/MAP 仍证明 256 B 区位于 `0x20207F00`、属性为 `UNINIT`、load address 为 `-`，且未与栈或普通 ZI 重叠。`UNINIT` 只阻止 C 启动代码初始化该区，不能改变 BOOTRST 的 SRAM 断电语义。
- 因此当前可靠边界是：短按 NRST、软件 BOOTRST 和 WWDT0 这类 BOOTRST 只能依赖 4 B coarse breadcrumb；256 B detailed 与 HardFault scratch 仅可在不清 SRAM 的 SYSRST/CPURST 路径上尽力恢复，仍须分别上板验证。若将来要求 WWDT/NRST 后恢复更多上下文，需重新设计 4 B 位打包或使用其他非 SRAM 持久介质，不能靠 `.noinit`。
- 复位后约 30.97 s 的空闲快照仍为 Safety IDLE，故障、目标、请求/应用 PWM、四级任务漏期、UART/遥测 drop 和格式错误均为 0。本次未启动电机、改参、写 Flash 或再次下载。

- 约 31.1 s 的空闲快照为 Safety IDLE，故障、目标、请求/应用 PWM、四级任务漏期、UART/遥测 drop 和格式错误均为 0。本次未启动电机、改参、写 Flash 或再次下载。

## 受控 SYSRST / WWDT 验收镜像

为完成软件复位和看门狗分类验证而不在正式固件暴露危险命令，复用了既有 `M2_FAULT_INJECTION_TEST` 隔离构建并收紧安全边界：

- 测试镜像使用独立身份 `M6-runtime-20260726-r12-fi`；正式 target 未定义该宏，仍报告 `M6-runtime-20260726-r12`，且不包含以下入口。
- 仅测试镜像的大写 `Z` 调用既有 `ResetDiag_HardFaultReset()`：先要求系统为 IDLE、无故障、所有诊断/巡线动作空闲且尚未停喂狗，再通过 `Safety_StopMotor()` 直接制动，随后写 HardFault scratch 并请求 SYSRST。
- `Z` 传入空 stacked frame，预期恢复的 PC/LR/xPSR 全为 0。它只能验证 raw `0x1B software_sys` 分类、SYSRST 下 `.noinit` detailed 保持和合成 scratch 恢复；不能据此宣称真实 HardFault 异常向量或栈帧捕获已通过。
- 既有大写 `W` 同样增加上述门控和直接制动，再停止喂狗并进入只重复 Safety 制动与 `WFI` 的等待循环，不再返回主循环或处理排队的动作命令；UART RX ISR 的裸 `S`/空格仍可抢占。提示语明确区分预期 raw `0x0E wwdt0` 与重启后 Safety watchdog fault bit `0x20`。WWDT 周期、门限和正式健康门控均未放宽。
- UART RX ISR 对裸 `S`/空格的抢占逻辑未改；参数事务、Flash A/B、控制参数和车辆动作路径未改。

故障注入构建脚本现在是纯构建脚本，不再提供 `-Flash` 或任何下载调用。它会在正式 `.uvoptx` 存在时生成匹配的 `fault_injection.generated.uvoptx`，把 target 名同步为 `m2_fault_injection`，再复用正式下载脚本的完整断言验证 current target、Use Target、CMSIS-AGDI、Horco `4041840e`、Flash sequence/算法、SWD protocol 和 1 MHz；正式工程文件不被脚本改写。当前生成工程的 IROM 为 `0x1F800`。本轮正式 r12 的命令行下载周期已用尽两次失败上限，后续只允许用户手动下载精确生成工程。

验证结果：

- `scripts/test.ps1`：97/97 通过。
- 正式 r12 ARMCLANG 6.22 Rebuild：`Code=43580, RO-data=9416, RW-data=8, ZI-data=25704`，0 error、0 warning；最高普通字节仍为 `0xCF0F`。
- `r12-fi` 首轮 Rebuild 因测试专用等待循环使用 `__WFI()` 而 `diagnostics.c` 尚未引入其声明失败；根因定位后仅在 `M2_FAULT_INJECTION_TEST` 下引入现有 `ti_msp_dl_config.h`，未改变正式编译路径。复测为 `Code=43620, RO-data=9432, RW-data=8, ZI-data=25696`，0 error、0 warning；最高普通字节 `0xCF47`，低于参数区 `0x1F800`。MAP 仍显示 `RW_NOINIT` 位于 `0x20207F00`、大小 `0x100`、属性 `UNINIT`、load address 为 `-`。
- AXF 字符串复核在测试镜像中找到独立 `r12-fi` 身份、测试构建警告、`Z`/`W` 帮助和修正后的 WWDT 提示，并确认正式 r12 AXF 中这些字符串全部不存在。该结论是下载前的构建隔离证据，不替代下述上板结果。

上板顺序固定为：手动下载精确 `keil/fault_injection.generated.uvprojx` 并先核对 `r12-fi`/IDLE/PWM 0；等待至少两个 20 ms 健康窗口后发 `Z`，先取完整 `v/c`；再次等待至少两个健康窗口后发 `W`，复位后先取完整 `v/c`，不得先清 `0x20`；最后立即手动恢复正式 r12，并以精确身份及帮助中不存在 `TEST ONLY` 双重确认测试入口已经移除。WWDT 必须最后测试，因为其 BOOTRST 会清 SRAM detailed。

## 受控 SYSRST / WWDT 上板结果

用户手动下载精确生成工程后，COM10 首先确认：

```json
{"firmware": "M6-runtime-20260726-r12-fi", "generation": 0, "port": "COM10", "revision": 1, "schema": 1, "source": "defaults"}
```

帮助中同时存在 `FAULT INJECTION BUILD`、`TEST ONLY: Z=SYSRST breadcrumb W=stop watchdog`；预检快照为 raw `0x01 por_or_parity`、Safety IDLE、故障/PWM/目标 0、四级任务漏期 0、UART/遥测 drop 和格式错误 0。等待时间远大于两个 20 ms 健康窗口后才发送 `Z`。

`Z` 复位后的完整关键证据为：

```text
RESET raw=0x1B cause=software_sys class=software boot=2 checkpoint=control_rx prev_coarse=1 prev_detail=1 hardfault=1
RESETCTX prev_boot8=1 prev_boot=1 prev_cp=hardfault detail_cp=task20 seq=2530 time=50580 wwdt=50580 hf_pc=0x00000000 hf_lr=0x00000000 hf_xpsr=0x00000000
RESETIO faults=0x00000000 miss=0 drop=0/0/0 pending=0x00 missed=0x00 state=2 q=0 health=0x07
SAFETY state=IDLE faults=0x00000000 first=0 last=0 action=0 deadline=0 pwm=0,0
CONTEXT target=0,0 speed=0,0 requested_pwm=0,0
SCHED release=2222/1111/555/111 miss=0/0/0/0 pending=0x03
COMM tx=2635 rx=110 tx_drop=0 rx_drop=0 format=0 baud=115200 8N1
```

raw `0x1B software_sys` 与 software class 正确；4 B coarse、256 B detailed 和合成 HardFault scratch 均跨 SYSRST 恢复，previous boot ID 一致。PC/LR/xPSR 全 0 与空 stacked frame 的测试设计一致，不能外推为真实 HardFault 栈捕获。`SCHED pending=0x03` 是冻结瞬间已有 5/10 ms 周期任务到期，`miss=0/0/0/0` 且 reset 前 `RESETIO pending/missed=0`；没有据此认定漏期。复位后身份仍精确为 `r12-fi`，Safety IDLE、PWM/目标 0，UART 无丢包或格式错误。

再次等待超过两个健康窗口后发送 `W`。测试提示完整发出，随后原 WWDT 在未放宽周期/窗口的条件下复位：

```text
TEST watchdog stopped: zero PWM; expect raw 0x0E; post-boot fault 0x20.
RESET raw=0x0E cause=wwdt0 class=watchdog boot=3 checkpoint=control_rx prev_coarse=1 prev_detail=0 hardfault=0
RESETCTX prev_boot8=2 prev_boot=0 prev_cp=tx_submit detail_cp=none seq=0 time=0 wwdt=0 hf_pc=0x00000000 hf_lr=0x00000000 hf_xpsr=0x00000000
RESETIO faults=0x00000000 miss=0 drop=0/0/0 pending=0x00 missed=0x00 state=0 q=0 health=0x00
SAFETY state=FAULT faults=0x00000020 first=0 last=0 action=0 deadline=0 pwm=0,0
CONTEXT target=0,0 speed=0,0 requested_pwm=0,0
SCHED release=4349/2174/1087/217 miss=0/0/0/0 pending=0x01
COMM tx=2598 rx=110 tx_drop=0 rx_drop=0 format=0 baud=115200 8N1
```

raw `0x0E wwdt0`、watchdog class 和 Safety `0x20` 均正确；复位前最后 coarse checkpoint 为 `tx_submit`，符合提示提交后停喂狗。BOOTRST 保留 coarse、清除 detailed/HardFault scratch，与短按 NRST 的硬件边界一致。故障状态下 PWM、目标、漏期、UART/遥测 drop 和格式错误仍为 0；取证前没有发送 `x` 清故障。测试后立即要求用户手动恢复正式 r12，正式身份与测试入口移除仍须在恢复后核对。

## 当前结论与下一入口

r12 reset diagnostics 已完成主机模型、全量回归、正式目标构建、MAP/HEX 边界，以及 power、短按 NRST/BOOTRST、长按 NRST/POR、受控 SYSRST 和 WWDT 的实际 raw cause/保持边界核对。受控 `Z/W` 后均保持零 PWM、零目标、零任务漏期与零 UART/遥测丢包；SYSRST 的 detailed/合成 scratch 恢复和 WWDT 的 coarse-only 恢复已经硬件通过，但真实 HardFault 异常栈仍未验证。用户此前观察到的无征兆停车仍缺当时证据，不能追溯归因；本次受控 WWDT 只证明诊断链能在复现时明确归类，不证明历史停车就是 WWDT。

当前 MCU 仍运行 `r12-fi` 且 Safety 锁存 `0x20`。下一入口只有手动恢复正式 r12，并以精确身份、参数来源、Safety/任务/UART 快照和帮助中无 `TEST ONLY` 完成退出核对；不得再发命令行下载。恢复后再进入日志频率矩阵、统一 V2 二进制传输层和 Python `m6link`。
