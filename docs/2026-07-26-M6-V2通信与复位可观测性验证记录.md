# 2026-07-26 M6 V2 通信与复位可观测性验证记录

## 范围与安全边界

本记录承接 `M6-runtime-20260726-r11`，后续主目标调整为高速直线、平滑弧线、高速陀螺仪角度控制和系统长期无复位。赛题与赛道公布前，不再为未知直角弯试验新的纯巡线失线搜索参数。

通信重构和主机工具必须持续满足以下边界：

- UART RX ISR 中单字节 `S`/空格继续立即急停，不等待协议解帧、CRC、队列或主机确认；
- 所有电机输出继续经过 `System/safety.c`，不得旁路 Safety 仲裁；
- WWDT 周期和健康窗口不放宽，不增加无条件喂狗路径；
- 周期任务不得调用 `printf`/`snprintf`/`vsnprintf`，不得阻塞等待串口；
- 高速实车按 `160→180→200→220→250 mm/s` 分级，任一级出现复位、故障、漏期、异常丢包、持续饱和或明显振荡立即回退。

## r11 上板身份核对

用户已在 Keil 中手动下载工作树生成的最新镜像。本轮没有发起命令行下载，也没有消耗命令行下载重试次数。COM10 枚举为 Horco USB 串行设备，父设备序列号仍为 `4041840E`。

使用只读探针精确约束固件 ID 和 schema：

```powershell
python scripts/m6_tune.py --port COM10 --firmware-id M6-runtime-20260726-r11 --schema 1 --timeout 1.5 probe --json
```

返回：

```json
{"firmware": "M6-runtime-20260726-r11", "generation": 0, "port": "COM10", "revision": 1, "schema": 1, "source": "defaults"}
```

这证明当前实际运行镜像为精确 `r11`，参数 schema 为 1，启动参数来自编译默认值，尚无已加载的持久化代次。

接管工作树时，`keil/empty_LP_MSPM0G3507_nortos_keil.uvprojx` 的 IROM 显示 Size 再次被手动 Keil 会话改为 `0x20000`；同一文件的 OCR 区和实际使用的 `keil/mspm0g3507.sct` 仍为 `0x1F800`，因此此前 r11 的 MAP/HEX 边界证据不受该显示漂移影响。为防止后续配置退化，已在任何新构建前把 IROM Size 恢复为 `0x1F800`；该文件其余既存改动保持不变。

## 空闲 Safety、任务与 UART 快照

只发送无动作的 `v` 和 `c` 诊断命令，得到：

```text
SAFETY state=IDLE faults=0x00000000 first=0 last=0 action=0 deadline=0 pwm=0,0
CONTEXT target=0,0 speed=0,0 requested_pwm=0,0
SCHED release=71488/35744/17872/3574 miss=0/0/0/0 pending=0x00
COMM tx=1750 rx=110 tx_drop=0 rx_drop=0 format=0 baud=115200 8N1
```

结论：

- Safety 为 `IDLE`，无锁存故障，无活动动作，目标、请求 PWM 和应用 PWM 均为 0；
- 5/10/20/100 ms 任务释放计数对应本次启动已运行约 357 s，四级漏期均为 0；
- UART TX/RX 丢包和格式错误均为 0；
- 本次核对没有启动电机、应用参数或写入 Flash。

## MCU reset cause 诊断边界

源码和本仓库所带 TI DriverLib 共同证明：

1. `Source/main.c` 在任何初始化前调用一次 `DL_SYSCTL_getResetCause()`；MSPM0G1x0x/G3x0x 的 `RSTCAUSE.ID` 是 read-to-clear 字段。
2. 当前代码只用 `Hardware/watchdog.c::Watchdog_WasResetCause()` 判断精确的 `DL_SYSCTL_RESET_CAUSE_SYSRST_WWDT0_VIOLATION`，命中时锁存 `SAFETY_FAULT_WATCHDOG_RESET=0x20`。
3. 原始 reset cause 随后被丢弃，既不保存也不通过 UART 上报；当前没有跨复位 breadcrumb。
4. 本次 Safety 故障为 0，因此可排除“当前这次启动由 WWDT0 复位且仍未清故障”。但 r11 无法进一步区分这次启动来自上电/BOR、长短 NRST、软件复位、调试器复位或其他系统复位，不能把其中任何一种写成已确认原因。

芯片枚举本身能够区分上电/供电异常、外部 NRST、软件 POR/BOOTRST/SYSRST/CPURST、WWDT、调试器和硬件故障。DriverLib 还提供 4 字节 `SHUTDNSTORE`，并明确这些字节在 BOR、BOOTRST 和 SYSRST 后保持且由硬件做奇偶校验；这为不写 Flash 的紧凑复位前 breadcrumb 提供了依据。真正 POR 后的 breadcrumb 不能假定有效，必须结合 reset cause 和记录标识判定。

## 当前结论与下一入口

r11 的身份、schema、参数来源、Safety、任务计数和 UART 空闲状态已完成上板核对；当前没有 WWDT、漏期或丢包证据。用户此前观察到的无征兆停车仍缺当时的 reset cause 和复位前执行阶段，不能追溯归因。

下一实现切片先增加独立 reset diagnostics：在最早启动点保留原始 reset cause，分类上电、外部、软件、WWDT、调试器和硬件故障，并用 `SHUTDNSTORE` 保存有界执行阶段 breadcrumb。该切片先通过主机测试和 Keil 构建，再上板分别验证可安全触发的复位类型；不会以延长/关闭 WWDT 作为通过条件。随后再进入统一 V2 二进制传输层和 Python `m6link`。

完整线协议、优先级/背压、主机库、GUI 边界和 R0–R7 实施切片见 `docs/2026-07-26-M6-V2通信架构设计与实施计划.md`。本次新增设计文档本身无固件功能变化，未据此宣称新的主机测试、目标构建或硬件通过。
