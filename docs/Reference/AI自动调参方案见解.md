## 结论

能实现，而且你的仓库已经具备大部分底座。不过要把目标分成两种：

1. **比赛前的全自动硬件在环调参**：允许执行较多轮测试，自动寻找轮速、航向、巡线和速度参数。
2. **比赛现场的快速适配**：加载最接近的已验证参数档案，只调整少量与赛道、光照和电池状态强相关的参数。

不建议把目标设成“比赛现场从默认值开始搜索全部 35 个参数，直到全局最优”。这种流程耗时、容易过拟合，也可能因为一次危险候选参数而中断。更现实的目标是：

> 把车放到赛道上，按一次物理使能键，自动低速探路、微调少量参数、验证两圈，随后锁定参数进入比赛状态。

这是可以做出来的。

你的当前仓库已经有统一的 `m6link.Session`、V2 遥测、网页控制、动作执行、参数暂存与应用、录制回放、安全门控和评分函数。网页、参数页、录制器都复用同一个串口会话，本地录制也已经是带 schema、索引和摘要的结构化数据，适合后续自动分析。

## 数据应该从串口读，而不是从网页“看”

推荐链路是：

```text
MSPM0G3507 固件
        │ UART0 / M6 V2
        ▼
m6link.Session  唯一串口所有者
        │
        ├── 网页仪表盘：显示、人工急停、查看结果
        ├── Recorder：保存完整试验数据
        └── AutotuneOrchestrator：自动试验与调参
                ├── SafetySupervisor
                ├── ExperimentRunner
                ├── Scorer
                ├── Optimizer
                └── ProfileStore
```

原因很明确：

* `Session` 已经负责串口发现、握手、V2 帧解析、事件队列、遥测队列和订阅管理，并且明确采用单后台线程持有串口，不自动重发 RPC。
* 当前网页的数据本身就是从 `Session` 解码后放入 `DashboardBuffer`，再通过 `/api/state` 等接口输出。网页不是数据源，只是数据的展示层。
* 网页的动作、参数和急停接口最终也只是调用同一 `Session`。

因此最简洁、效率最高的实现不是让 AI 识别网页上的曲线，也不是再开一个串口进程，而是让自动调参模块直接运行在当前 `m6link` Python 进程里。

过渡阶段可以让独立 AI 程序访问网页后端的 JSON API，但也应调用 API，不能解析 HTML 或截图。长期方案仍然应该直接共享 `Session`、录制器和控制器。

## 不要让大语言模型直接“拧参数”

这里真正需要的是一个**受安全约束的数值优化器**，不是让聊天模型根据几张曲线随意输出新的 Kp、Ki。

合理分工是：

* MSPM0G3507：继续执行确定性的 5 ms、10 ms、20 ms 控制任务、安全判断和电机门控。
* Python 主机：运行试验状态机、评分器和参数优化器。
* 大语言模型：可用于解释异常、总结试验、判断下一步应该开放哪个参数组，但不直接绕过参数边界、安全规则和动作协议。

你的主循环已经把轮速更新、安全评估和电机请求放在 5 ms 任务，把陀螺仪和灰度放在 10 ms 任务，把航向、巡线和 V2 遥测放在 20 ms 任务。AI 不应该进入这些实时环路。

## 一次自动试验应怎样执行

建议把每个候选参数试验固定为以下状态机：

```text
IDLE
 → PREFLIGHT
 → STAGE_PARAMETERS
 → APPLY
 → ARM
 → CONFIRM
 → RUN_AND_RECORD
 → NORMAL_STOP
 → SCORE
 → ACCEPT 或 REVERT
 → VALIDATE
 → SAVE_FINAL
```

具体过程如下。

### 1. 启动前检查

自动读取：

* 固件 ID、协议版本、参数 schema、boot ID；
* 当前 active/staged revision；
* Safety fault；
* 编码器、陀螺仪、灰度标定状态；
* UART、调度器、遥测丢包计数；
* 当前是否处于 IDLE；
* 物理自动调参使能键是否按下。

你的载板本身有三个板载按键，可以保留一个作为“允许自动运动”的物理使能，而不能仅依赖网页令牌。

### 2. 保存黄金基线

进入调参前，记录：

* 当前有效参数；
* 持久化代数；
* 固件版本；
* 测试场景；
* 起始电池状态；
* 当前传感器状态。

这个参数集称为 `golden profile`。任何通信异常、故障或主机退出，都必须能够回退到它。

### 3. 生成一个候选参数

候选必须满足：

* 固件已有的上下限；
* 参数间关系约束；
* 相对黄金参数的最大单步变化；
* 当前试验阶段允许修改的参数白名单。

当前仓库已经提供了 35 个运行期参数，包括轮速 PI、滤波、加减速、jerk、左右轮 kS/kV，航向直行与转向 PD，以及巡线速度、滤波、PD、修正限幅和曲线增益。

固件还已经检查了诸如：

* `line.speed_min <= line.speed_max`
* `kS + kV × 400 <= 680`
* 遥控速度低、中、高有序

这些约束必须继续由固件作为最终判定，主机优化器只做第一层过滤。

### 4. 只暂存并应用，不立即保存

候选参数先 `stage`，然后在安全的 IDLE 或诊断边界 `apply`。当前参数系统已经区分 staged 和 active，轮速诊断期间的增益还可以在下一个 5 ms 边界提交。

控制运行层已经能把 active 参数直接映射到轮速、航向、巡线和遥控模块，因此这些参数调整不需要重新编译和烧录。

候选试验期间不要执行 `save`。只有最终参数经过重复验证后才保存一次。参数存储目前是两个 1 KB 冗余槽，适合保存最终结果，不适合每个候选都擦写。

### 5. 使用现有动作协议执行测试

自动调参器应只调用已经受 Safety 保护的动作：

* `WHEEL_SPEED_TEST`
* `HEADING_HOLD`
* `HEADING_TURN`
* `HEADING_RATE`
* `LINE_FOLLOW`

不能新增“AI 直接写 PWM”的旁路。当前网页控制器已经对这些动作实施 Arm、Confirm、持续时间、故障状态和能力检查。

完整自动化时，仍应保留一次会话级物理授权：

1. 用户把车放在封闭赛道；
2. 按下板载“自动调参允许”键；
3. 主机获得一段有限时间的自动 Arm/Confirm 权限；
4. 一旦故障、重新上电或链路断开，权限失效；
5. 不允许自动清除新的 Safety 故障。

这比取消 Arm/Confirm 更安全。当前 V2 CLI 明确拒绝自动执行 `tune-wheel`，就是因为尚未建立这种机器授权边界。

### 6. 直接录制 V2 遥测

现有遥测已经足够支撑第一版优化器：

* CORE：请求速度、实际速度、PWM、偏航角、角速度、饱和和故障；
* WHEEL：原始/滤波速度、误差、P/I/FF 分量、斜坡目标、PWM、饱和时长、编码器增量；
* LINE：八路 ADC、有效通道、聚类、位置、置信度、导数、动态基础速度、修正量和丢线时长；
* HEALTH：复位、安全故障、调度超期、UART 丢包、遥测丢包和队列水位。

推荐录制频率继续采用仓库现有设置：

* CORE：20 ms；
* WHEEL：40 ms；
* LINE：40～60 ms；
* HEALTH：1000 ms。

现有 V2 Recorder 也已经能把这些流合并为旧评分器兼容的数据，并把遥测 gap 视为硬失败。

### 7. 先做硬失败判断，再评分

硬失败应直接停止本轮，而不是继续计算“还不错的分数”：

* 任意 Safety fault；
* 编码器无效或堵转；
* 持续 PWM 饱和；
* 丢线超过自动调参专用阈值；
* 调度任务超期；
* UART 或遥测丢包；
* 帧序号 gap；
* 主机不知道动作是否已经执行；
* 小车超出赛道边界。

当前评分器已经把故障、持续饱和、丢线、调度超期、UART 丢包、遥测丢包和遥测间隙设为硬失败，并计算上升时间、超调、稳态误差、振荡、偏航 RMS、巡线位置 RMS 和修正 jerk。

进一步建议采用分层目标，而不是只用一个加权和：

1. 无故障且完成试验；
2. 不丢线、不过饱和；
3. 完成时间或单圈时间最短；
4. 位置误差和偏航误差最小；
5. 动作平滑、PWM 余量充足。

这样优化器不会为了少量速度提升而接受明显危险的参数。

### 8. 接受或回滚

普通性能不佳的候选：

* 正常停止；
* stage 回当前最佳值；
* apply；
* 继续下一候选。

出现硬失败的候选：

* 立即急停；
* 终止整个自动调参会话；
* 保留故障、录制和候选参数；
* 等待人工检查，不能自动清故障后继续跑。

现有搜索器已经具备“不接受就回滚，异常时急停并恢复 accepted 参数”的思路。

## 参数必须分组调，不能 35 个一起搜索

建议顺序固定为：

### 第一阶段：传感器和机械标定

先确认：

* 轮径和左右编码器每圈计数；
* 左右轮方向；
* 灰度白底/黑线标定；
* 陀螺仪零偏；
* 电机无负载和落地差异。

当前轮径和编码器每圈计数仍是编译期常量。

灰度标定目前也是两阶段人工流程：分别把八路探头放在白底和黑线上，各采 64 个样本，然后生成编译期宏。

因此，当前版本还不能仅靠“随手放在任意赛道上”完成完整灰度重新标定。要做到真正一键适配，未来需要二选一：

* 赛道起点设置已知的白底区和黑线标定区；
* 将灰度白/黑基准和阈值改成可运行期更新、可持久化的数据。

### 第二阶段：轮速前馈

先在架空或安全直道以 100、160、220、300 mm/s 采样，拟合：

```text
PWM = kS + kV × speed
```

你的仓库已经有四速度点的 kS/kV 拟合与多速度验证逻辑。

前馈先准确，PI 就不需要承担大部分静态输出，调参速度会快很多。

### 第三阶段：轮速 PI、滤波和斜坡

小范围调整：

* 左右 Kp；
* 左右 Ki；
* `filter_alpha`；
* 必要时 accel、decel、jerk。

先调单轮，再调双轮同步，最后落地验证。

### 第四阶段：航向

在轮速已经稳定后调整：

* `heading.straight.kp/kd`
* `heading.turn.kp/kd`
* `rate_alpha`
* `correction_limit`
* `turn_speed`
* `smooth_zone`

否则航向优化器会用航向参数补偿轮速层的问题。

### 第五阶段：低速巡线

固定较低速度，调整：

* position/derivative filter；
* line Kp/Kd；
* correction limit；
* correction slew；
* curve gain。

### 第六阶段：速度包络

控制器稳定后，才增加：

* `line.speed_min`
* `line.speed_max`
* 曲线降速策略
* 丢线搜索速度

这样参数空间始终保持在 2～6 维，而不是一次优化全部 35 维。

## 怎样让搜索更快

仓库当前的坐标搜索每轮对每个参数测试正、负两个方向，最多三轮。四个轮速 PI 参数理论上最多是：

```text
1 次基线 + 3 轮 × 4 参数 × 2 个方向 = 25 次测试
```

当前轮速测试要求至少 7 秒，因此仅四个参数的最短动作时间就接近 3 分钟。若把 35 个参数全放进去，则是最多 211 次测试，单动作时间已经超过 24 分钟，还没有计入停车、应用、重新开始和验证。

所以高效方案不是让 AI 搜得更“聪明”，而是减少需要真实试车的维度：

* 能拟合的参数直接通过系统辨识求出，例如 kS/kV；
* 第一版继续用当前坐标搜索，因为简单、可解释、容易回滚；
* 后续每个参数组可换成受约束的贝叶斯优化或 TPE；
* 候选先运行短筛选，明显差的提前结束；
* 只有前几名执行完整单圈验证；
* 最终结果必须在不同起点、至少两次重复运行中仍然有效；
* 使用中位数或较差一次成绩，而不是只取最好一次。

大语言模型可以根据记录决定“下一轮重点调轮速还是巡线”，但候选生成应由确定性的边界优化器完成。

## 比赛时的一键快速适配方案

比赛现场推荐采用下面的流程，而不是完整重新调车。

### 1. 加载最接近的参数档案

赛前建立参数档案库，例如：

* 光滑白板；
* 哑光赛道；
* 强光；
* 弱光；
* 满电；
* 中等电量；
* 新轮胎；
* 磨损轮胎。

档案保存在主机侧，车上只保留一个稳定黄金版本和最终接受版本。

### 2. 原地环境识别

静止采集几秒：

* 八路 ADC 白底水平和噪声；
* 陀螺仪零偏；
* 编码器静止噪声；
* 链路丢包；
* 当前参数与档案差异。

然后选择最接近的档案，不从默认值开始。

### 3. 一圈低速探路

使用保守速度跑一圈，采集：

* 直线与弯道的 line position；
* confidence；
* correction；
* active count 和 cluster count；
* 偏航角速度；
* 丢线位置；
* 每段可安全达到的速度。

这里最好增加一个明确的起终点标记。当前遥测没有绝对赛道位置或可靠单圈计时，只靠内部误差，优化器可能得到“传感器曲线很好看，但实际圈速并不好”的结果。

可选办法包括：

* 起终点特殊灰度图案；
* 红外门；
* 磁标；
* 外部摄像头；
* 视觉模块报告赛道进度。

### 4. 只开放 2～4 个参数

现场通常只需要调整：

* `line.speed_max`
* `line.kp` 或 `line.kd`
* `line.correction_limit`
* `line.curve_gain`

其他轮速、机械、航向基础参数应在比赛前冻结。

### 5. 两次验证后锁定

候选通过后再跑两次：

* 没有故障；
* 没有持续饱和；
* 没有遥测 gap；
* 没有长时间丢线；
* 成绩稳定；
* 比黄金参数有明确提升。

随后保存一次，并进入 `RACE_LOCKED` 状态。正式计分运行期间停止自动学习，防止参数因一次异常样本继续漂移。

这种流程所需时间主要是一圈探路加两圈验证。若赛道较短、赛前档案足够接近，确实可以达到“放上去，过一会儿自动调好”的体验。

## 当前还缺少的关键部分

从现在的仓库状态看，主要缺口不是底层控制，而是自动试验编排：

1. **V2 自动动作授权**
   目前 V2 有完整 Arm/Confirm，但 CLI 故意不允许机器自动 Confirm。需要新增带物理使能和超时的自动调参会话权限，而不是直接删除确认。

2. **自动调参状态机**
   需要把 stage、apply、arm、confirm、record、score、revert 串成一个不可跳步的状态机。

3. **运行期灰度标定**
   当前白底/黑线标定仍产生编译期配置，不能自动适应完全不同的赛道表面。

4. **真实比赛目标信号**
   需要可靠单圈时间或赛道位置，而不仅是 line position RMS。

5. **电池状态**
   当前 V2 流没有电池电压。电机前馈、加速和最高速度都会受到电池压降影响。后续最好把电池电压加入遥测或通过外部模块提供。

6. **参数档案管理**
   当前双槽存储用于可靠保存，不是多场景参数库。参数档案更适合保存在主机侧，最终结果才写入车上。

## 最合理的实施顺序

第一步先做**离线自动评估**：读取现有录制，验证评分规则能否把“实际更好”和“看起来更好”区分开。

第二步做**V2 半自动轮速调参**：用户只在会话开始时进行一次物理授权，之后机器自动完成多轮候选测试和回滚。

第三步加入**航向和低速巡线自动调参**，同时增加起终点标记和赛道成绩。

第四步建立**参数档案库和比赛快速适配模式**。

第五步才考虑更复杂的贝叶斯优化、外部视觉定位或近似车辆模型。

最终可实现的实用版本不是“AI 保证找到数学意义上的全局最优”，而是：

> 在规定赛道、当前电池、轮胎和光照条件下，自动找到满足所有安全约束、重复运行稳定、并且比赛指标优于黄金基线的参数组合。

这个目标更可靠，也更适合比赛。
