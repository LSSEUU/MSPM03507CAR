# 2026-07-26 M6 V2 通信架构设计与实施计划

## 1. 目标与非目标

本设计服务于四个后续目标：高速直线、平滑左右弧线、高速陀螺仪角度/角速度控制，以及系统长期无复位。统一链路必须同时供 CLI、桌面 GUI、自动调参和 AI 调车使用。

本轮不重新设计未知赛道的纯巡线直角弯搜索；`r11` 的失线飞行记录器保留供赛题公布后的根因分析。V2 也不改变轮速、航向、巡线或 Safety 的控制律。

截至 2026-07-26，R0/R1 的 reset 取证已经完成，当前 MCU 已恢复正式 r12；R2 热路径清理已在待上板 r13 源码完成并通过主机/目标构建，尚未下载。下一实现入口是先冻结完整 wire registry、消息字段与 C/Python golden vectors，再进入 R3；后续顺序固定为 V2 → `m6link` → GUI → 日志负载矩阵 → 分级轮速/弧线 → 高速航向 → 保存与 PB11 回归。

不可破坏的边界：

- UART RX ISR 对裸 `S`/空格立即急停；急停不依赖解帧、CRC、队列、主机线程或 ACK。
- 所有电机请求仍由 `System/safety.c` 仲裁，`Motor_SetPWM()` 仍只有 Safety 一个运行期所有者。
- WWDT 继续约 31 ms，仅由 5/10/20 ms 健康窗口喂养；参数 Flash RAM 写入器的特殊喂狗边界保持不变。
- 5/10/20/100 ms 周期任务只采集固定大小快照或事件，不调用 `printf`、`snprintf`、`vsnprintf`，不等待串口。
- 所有队列固定容量、无动态内存；控制回复不能被遥测占满或静默丢弃。
- 有副作用命令不能因超时被主机盲重发；断线时必须能报告“结果未知”。

## 2. 现状诊断

### 2.1 已经正确的部分

- RX ISR 已对 `S`/空格做无状态抢占，并通过 emergency epoch 使旧参数解析器丢弃半帧和待提交 apply。
- M6 遥测在 20 ms 任务中只复制快照，CSV 编码和发送在后台进行。
- `debug_try_write()` 只能整块入队或拒绝，适合作为“完整线帧提交”底层原语。
- 参数 apply 在 5 ms 边界提交；save 由固件检查 IDLE、无故障、无动作和电机制动。
- 主机事务当前只写一次，超时只继续读取匹配 ID 的回复，不自动重发运动或保存命令。

### 2.2 R2 前诊断出的缺口

- `RSTCAUSE` 为 read-to-clear；r11 只判断 WWDT0，其他原因和原始值被丢弃，也没有跨复位 breadcrumb 或 boot/session ID。
- 旧事务只有文本 ID，没有 CRC、帧超时、重复请求去重或回复预留；回复队列满时会静默丢弃。
- RX 环有效容量 63 字节，而旧事务最大线上长度约 60 字节；`Diagnostics_Poll()` 每轮只取一个字节，积压时仍可能进入 `WFI`。
- 旧诊断、回复、CSV 和批量 G6 共用 1024 字节 TX FIFO；一旦低优先级数据已入 FIFO，无法让控制回复越过。
- `debug_printf()` 逐字节入队，拥塞时会产生残缺文本；`Diagnostics_Task100ms()` 和 `AppRemote_Task20ms()` 仍存在周期任务内格式化/输出。
- 115200 8N1 的理论有效上限约 11520 B/s。现有 164 字节快照即使无帧头、无转义地以 50 Hz 发送，也需要 8200 B/s，约占 71%；不能把它原样迁移为一个 V2 高频帧。
- 1,551 行 `scripts/m6_tune.py` 同时承担串口、事务、记录、评分、调参和 CLI；多个消费者无法安全共享同一串口读者。

r12 已关闭首项 reset cause/breadcrumb 缺口；待上板 r13 已关闭 RX 容量/消费预算、RX 积压睡眠以及 20/100 ms 周期任务输出缺口。旧回复预留、TX 单帧优先调度、V2 完整性/幂等和单 Session 主机所有权仍属于 R3–R5。

## 3. 总体结构

```text
UART0 RX ISR
  ├─ 裸 S/空格 → emergency epoch → Safety 急停（永远最高优先级）
  └─ 其他字节 → RX ring
                    ↓
             transport router
          ┌─────────┴─────────┐
          │ legacy adapter    │ V2 codec/session
          └─────────┬─────────┘
                    ↓
             shared command service
                    ↓
        参数 5 ms 提交 / Safety / 动作服务

周期任务 → 固定快照/事件 → P0/P1/P2/P3 有界队列
                              ↓
                    后台消息编码与选优
                              ↓
              UART 每次只提交一个完整线帧
```

建议固件边界：

- `Hardware/uart_debug.c/.h`：只保留 UART ISR、裸急停、RX/TX 环和统计；增加批量 RX、loss epoch、TX 空间/拒绝计数。
- `System/reset_diag.c/.h`：reset cause、boot ID、粗/细 breadcrumb 和只读快照。
- `System/m6_transport.c/.h`：V2 codec、CRC、legacy/V2 路由、session/sequence、优先队列和背压。
- `System/m6_messages.c/.h`：逐字段小端编码，不直接发送 C struct。
- `System/control_service.c/.h`：参数/状态/动作的共享业务语义；旧 ASCII 和 V2 RPC 共用。
- `System/m6_telemetry.c`：保留固定快照，改为拆分的紧凑消息；CSV 只作为 P3 兼容输出。
- `System/diagnostics.c`、`App/app_remote.c`：周期路径只投递事件，旧文本格式化移到有预算的后台适配器。

## 4. reset cause 与 breadcrumb

### 4.1 不可变启动快照

`main()` 在 `SYSCFG_DL_init()` 前只读取一次 `DL_SYSCTL_getResetCause()`，立即交给 `ResetDiag_EarlyInit()`。模块终生保留：

- raw reset cause；
- 分类：`power`、`external`、`software`、`watchdog`、`debug`、`hardware_fault`、`bsl`、`unknown`；
- 原因短名和 boot ID；
- 上一启动 breadcrumb 的有效性和内容。

`x` 只清 Safety 故障，不能清除 reset history。WWDT0 仍额外锁存 Safety `0x20`；其他 reset 类别先只报告，不自动改变现有运动 Safety 语义。原始码始终同时输出，避免把 `POR_HW_FAILURE` 过度解释为唯一的“冷上电”。

### 4.2 两级保留

一级为 4 字节 `SHUTDNSTORE`：

| 字节 | 含义 |
|---|---|
| 0 | magic `0xB6` |
| 1 | 固定 `0x49`，即 magic 的互补值，同时标识 format 1 |
| 2 | 最后粗粒度 checkpoint，单字节原子更新 |
| 3 | 8 位 boot ID |

DriverLib 明确这些字节跨 BOR、BOOTRST、SYSRST 保持，并由硬件做奇偶校验。启动先读取上一记录；若 raw cause 是任一 POR 级原因（`POR_HW_FAILURE`、长 NRST POR、软件 POR）或 magic 对无效，则一律不采信旧 breadcrumb。更新本次 boot 元数据时先把字节 1 写成无效值，再写 magic、boot ID 和 BOOT checkpoint，最后写 `0x49` 提交；若中途复位，下一次只会看到无效记录。正常运行的 checkpoint 只原子更新字节 2，详细 `.noinit` 槽中的 boot ID/CRC 用于交叉校验；不宣称四个独立字节构成硬件原子事务。checkpoint 至少覆盖 boot、主循环空闲、5/10/20/100 ms、control RX、TX encode/submit、telemetry、OLED、parameter flash、WWDT service、Safety fault 和 HardFault。

二级为专用 `.noinit` SRAM 双槽记录：每槽有 magic、version、length、sequence、boot ID、time、checkpoint、最近健康喂狗、scheduler、Safety、UART/遥测队列与 drop 摘要，以及最后提交 CRC。先写数据，最后写 commit/CRC；启动选择最新有效槽。它是“尽力恢复”的详细证据，必须通过 SYSRST、短/长 NRST、WWDT 和断电上板试验界定实际保持范围，不能由源码检查直接宣称硬件保持。

周期热点不持续计算大 CRC：每个 20 ms 健康窗口提交一次详细快照；各风险阶段只更新 O(1) 的 RAM checkpoint 和单字节 `SHUTDNSTORE`。HardFault 仅写固定字段、最小异常寄存器和粗 checkpoint，执行内存屏障后主动请求 SYSRST；不依赖可能尚未初始化或因调试暂停而冻结的 WWDT，也不在异常上下文打印。复位后 raw cause 仍报告软件 SYSRST，同时 breadcrumb 明确标记 HardFault。

## 5. V2 线协议

### 5.1 安全协商

设备复位后默认保持 V1 文本模式，保证现有 `m6_tune.py` 和 `flash.ps1` 可用。主机不得向未知/r11 固件盲发二进制：

1. 先用旧事务安全查询 `meta.capabilities`；旧固件只会在 `:` 文本帧内返回未知键，不会把其中字符解释成动作命令。
2. 支持 V2 的固件返回能力位；主机再发送旧事务 `mode,v2`。切换只允许 IDLE、无故障、无动作、无待提交参数事务时开始。
3. 固件先冻结新的 V1 P2/P3 输出并等待既有 TX 排空，再把带一次性 nonce 的 `v2-ready` 作为最后一个完整 V1 回复；从接受切换请求起，RX 已进入隔离态，除裸 `S`/空格外的后续字节绝不再交给旧单字节命令。
4. `v2-ready` 物理发送完成后进入短时 `V2_ARMED`，全部非急停字节只进入 V2 候选解码器。有效 HELLO 回显 nonce 后建立 session。
5. HELLO 超时、超长、CRC 失败、RX overflow 或 emergency epoch 改变时不得立刻把剩余字节路由回 V1：先清除候选帧和 RX 环，进入 `V1_RESYNC` 静默隔离窗；只有 RX/TX 均空闲且连续保护时间内没有新字节，才允许一个严格的 `:` 身份/能力事务完成重同步。在该事务成功前旧单字节动作命令继续禁用。隔离期间新到的所有非急停字节只丢弃并刷新静默计时，不回放、不解释。

V2 session 中关闭旧非急停命令，避免噪声或残帧被解释为 `A`、`b` 等旧动作字符。退回 V1 只允许在 IDLE/无故障/无活动事务时显式执行，或设备复位。

### 5.2 帧格式

未转义内容：

```text
version:u8 (=2)
type:u8
flags:u8
session:u32 little-endian
sequence:u32 little-endian
payload_length:u16 little-endian (0..96)
payload[payload_length]
crc16_ccitt_false:u16 little-endian
```

线上使用 `0x7E` 起止、`0x7D` 转义，转义后继字节为原值 XOR `0x20`。必须对整个头、payload 和 CRC 转义四个值：`0x20`、`0x53`、`0x7D`、`0x7E`。合法 V2 帧内部因此永远没有裸空格或 `S`，ISR 急停语义无需变成有状态解析。

CRC 使用 CRC-16/CCITT-FALSE（poly `0x1021`、init `0xFFFF`），覆盖未转义头和 payload。payload 上限先固定 96 字节；最坏全转义线帧约 224 字节，约 19.5 ms 占线时间。P2/P3 消息应远小于最坏值，控制/故障帧保持短小。RX 环在 R2/R3 扩为至少 256 字节并采用有预算的批量/流式消费；每轮若 RX 仍非空不得直接 `WFI`，帧超时须大于最坏占线时间并通过最长关键任务延迟试验确定。

### 5.3 session、序号和命令幂等

- `mode,v2` 文本事务携带主机生成的 64 位随机 challenge；`v2-ready` 完整回显它。HELLO 前固定 `session=0, sequence=0`，HELLO payload 再携带 challenge。设备结合 challenge、boot ID 和 raw reset cause 派生并返回 32 位 session/boot token；后续请求从 sequence 1 开始。8 位 boot ID 只用于诊断，不承担新鲜性，session 新鲜性主要来自每次连接的新 challenge；这不是认证协议。
- session 在 HELLO 建立；challenge 不匹配、旧 session 或同 session 的异常回绕直接拒绝。32 位 sequence 回绕前必须重新协商 session。
- 主机请求使用 32 位 sequence；回复回显请求 sequence。
- 异步设备事件/遥测使用独立 TX sequence，主机用它识别丢包、重启和回绕。
- 固件至少维护 4 个请求表项，保存 session、sequence、请求 fingerprint、状态与结果；状态覆盖 `reserved`、`pending_boundary`、`completed`。完全重复的 sequence 在 5 ms apply 尚待提交时也只能关联原表项，不能再次排队；完成后只重发缓存结果，不再次执行 apply/save/动作。同 session/sequence 但 fingerprint 不同必须按完整性错误拒绝。
- 执行有副作用前必须先预留请求表项和最终回复槽。P1 另有一个遥测不可占用、可合并的专用 BUSY/NACK 槽；普通槽不足时请求不执行，只由该专用槽报告 busy，避免“没有回复槽却要求返回 busy”的循环。
- 断线或 ACK 丢失且无法由同 session 去重查询确认时，主机报告 `OutcomeUnknown`，不自动生成新 sequence 重试。

## 6. 优先级、背压和带宽

四级固定队列：

1. P0：reset report、Safety fault、watchdog breadcrumb 摘要；
2. P1：命令回复、身份、状态和参数事务结果；
3. P2：实时轮速、航向、灰度和控制遥测；
4. P3：旧文本、帮助、G6 和批量回放。

P0/P1 有保留槽，不能被 P2/P3 占用；P1 还保留独立 BUSY/NACK 槽。P2 使用“最新值优先、丢最旧”并累计明确 drop；P3 只能整条接收或整条丢弃。底层 UART 一次只提交一个完整线帧，帧结束后重新选最高优先级，避免提前把整批低优先级数据塞入 1024 字节 FIFO。急停后主循环在下一次选择前清空 P2/P3 backlog，历史遥测不得继续阻塞控制状态。

P2/P3 长期预算不超过约 8 KB/s（链路理论值约 70%），且发送调度器按实际转义后的 encoded wire length 扣减 token bucket，不按 payload 估算；剩余带宽保留给 P0/P1。首版订阅拆分为：

- 50 Hz：紧凑轮速、目标、PWM、航向核心；
- 10–25 Hz：灰度和巡线面板；
- 1–5 Hz：reset/Safety、任务、UART、队列和高水位健康；
- 按需 P3：参数定义、飞行记录、旧文本帮助。

主机首版控制窗口为 1。后续只有在 RX 环、CPU 占用和应答去重均取证后才扩大。

## 10. 验证矩阵

- reset：所有 raw cause 分类、`x` 后历史保留、SHUTDN/noinit 有效与无效、HardFault/WWDT 前 checkpoint。
- codec：0–255 全字节、任意分片/合并、翻位、截断、噪声、超长、重复界定符、序号回绕；任何合法线帧内部不得出现裸 `0x53`/`0x20`。
- emergency：idle、V1 半帧、V2 每个解析状态、TX 背压和 RX overflow 中的 `S`/空格均立即急停。
- commands：回复槽不足时不执行且专用槽可报告 busy；重复 apply/save 在预留、5 ms 待提交和完成后都只执行一次；ACK 丢失返回 OutcomeUnknown。
- mode switch：V1 TX 排空屏障、最后 READY、V2_ARMED、失败静默隔离和回到 V1 的每个边界都注入迟到/截断二进制字节，任何字节都不得触发旧 `A/b/x` 等命令。
- priority：填满 P2/P3 后 P0/P1 仍能入队并在当前帧结束后优先发送；全部 reject/drop/high-water 可观测。
- scheduler：周期调用图禁止格式化/发送；传输服务有固定预算；WWDT 服务位置与条件不变。
- host：单串口读者并发分流、慢 GUI、慢磁盘、断线重连、设备重启、V1 fallback、实时/回放同模型。
- 下载：首次命令失败后只原样重试一次，第二次失败停止，不切换方法或配置。
