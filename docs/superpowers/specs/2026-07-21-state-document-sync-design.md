# 项目状态文档与强制同步机制设计

日期：2026-07-21

## 1. 目标

使用根目录 `STATE.md` 取代已经过时的 `CODEREADME.md`，让仓库只有一个“当前实现状态”的权威来源。以后提交代码、外设配置、工程配置或构建工具变更时，必须在同一提交中同步更新 `STATE.md`。

本设计只管理当前状态，不取代以下文档：

- `docs/superpowers/specs/` 中经过批准的设计规范。
- `docs/superpowers/plans/` 中阶段性实施计划。
- `docs/` 中的数据手册、原理图和接线资料。
- Git 提交历史中的变更过程。

## 2. 文件变更

实施时完成以下变更：

| 文件 | 操作 | 职责 |
|---|---|---|
| `CODEREADME.md` | 删除 | 移除已经与源码不一致的旧解析文档 |
| `STATE.md` | 新建 | 唯一的当前功能、验证和问题状态文档 |
| `AGENTS.md` | 新建 | 约束 Codex 和其他仓库代理同步维护状态文档 |
| `.githooks/pre-commit` | 新建 | 检查暂存区中的工程变更是否同时包含 `STATE.md` |
| `scripts/setup_git_hooks.ps1` | 新建 | 为当前克隆设置 `core.hooksPath=.githooks` |

不修改用户当前未跟踪的其他文档，也不在本次迁移中修改固件代码。

## 3. STATE.md 内容结构

`STATE.md` 使用中文编写，并固定包含以下章节：

1. 文档职责和同步规则。
2. 项目目标与固定硬件。
3. 当前可运行的主程序流程。
4. 功能状态矩阵，区分“源码存在、已接入、已编译、已上板验证”。
5. 外设配置和引脚映射。
6. 串口命令与通信参数。
7. 构建、下载和验证状态。
8. 已知缺陷、风险和文档不一致。
9. 当前里程碑及下一步工作。
10. 最近验证记录。

状态描述必须使用可核验的措辞：

- `已实现`：源码中存在完整逻辑。
- `已接入`：当前主程序确实调用该逻辑。
- `语法已验证`：明确记录使用的检查命令和结果。
- `已编译`：必须有目标工具链的成功构建证据。
- `已上板验证`：必须有硬件测试步骤和结果。
- `未验证`：没有证据时的默认状态。
- `不可用`：存在空实现、未配置依赖或已知阻断问题。

不得根据函数名、旧文档或预期行为把功能写成已经完成。

## 4. AGENTS.md 维护规则

根目录 `AGENTS.md` 对整个仓库生效，并规定：

- 修改受监控的代码或工程文件时，必须在同一工作中更新 `STATE.md`。
- 新增、删除、启用、禁用功能时，更新功能状态矩阵和主流程。
- 修改引脚、波特率、定时器、PWM、任务周期或硬件接线时，更新对应配置章节。
- 修改串口命令或调参接口时，更新命令表。
- 修复或发现缺陷时，更新已知问题。
- 完成构建或上板测试时，只记录实际执行的命令、日期和结果。
- 纯文档、格式或不改变项目状态的注释修改不强制改变状态内容；若 Git 检查要求同步，可在最近验证记录中注明“无功能变化”。
- 不得通过删除检查脚本或使用跳过检查选项规避同步要求。

## 5. Git 提交检查

### 5.1 受监控范围

预提交脚本检查暂存区中的新增、修改、重命名和删除。下列路径或扩展名发生变化时，要求暂存区同时包含 `STATE.md`：

- `Source/`
- `Control/`
- `Hardware/`
- 未来的 `System/`、`App/`、`Config/`、`Tests/`
- `syscfg/`
- `keil/` 中的工程、链接和构建配置
- `.vscode/` 中的构建和调试配置
- `scripts/` 中的构建、下载、测试和工程辅助脚本
- 根目录下的 `.c`、`.h`、`.s`、`.syscfg`、`.uvprojx`、`.sct`、`.lds`、`.cmd` 工程文件

设计文档、PDF、普通 Markdown、图片和 Git 元数据不触发该要求。

### 5.2 判定规则

```text
暂存区没有受监控文件变化
    → 允许提交

暂存区包含受监控文件变化，且包含 STATE.md
    → 允许提交

暂存区包含受监控文件变化，但不包含 STATE.md
    → 拒绝提交并列出触发检查的文件
```

脚本只检查暂存区，避免未暂存的个人工作影响当前提交。`STATE.md` 的内容正确性由代码审查和 `AGENTS.md` 规则保证；预提交脚本只保证它与工程变更同时出现。

### 5.3 启用方式

Git 不会自动启用仓库内的自定义 hook。`scripts/setup_git_hooks.ps1` 在当前克隆中执行：

```powershell
git config --local core.hooksPath .githooks
```

脚本同时检查当前目录是否为仓库根目录，以及 `.githooks/pre-commit` 是否存在。每次新克隆仓库后执行一次。当前工作区在实施阶段也执行一次，并验证配置值。

Git 允许操作者通过特殊参数绕过本地 hook，因此该机制不能替代代码审查。仓库代理规则、提交检查和评审三者共同构成实际约束。

## 6. STATE.md 初始事实来源

初始内容以当前源码为主，并交叉核对工程文件和现有接线说明：

- 主流程和串口命令以 `Source/empty.c` 为准。
- 引脚、PWM 和 UART 配置以 `Source/ti_msp_dl_config.c/.h` 为准。
- 模块实现程度以 `Hardware/`、`Control/` 的调用关系为准。
- Keil 收录文件以 `.uvprojx` 为准。
- 上板状态只采用已有测试记录中的明确结论，并标记其证据来源。
- 相互冲突的旧说明进入“已知文档问题”，不得自行选择一个版本冒充实测结果。

初始状态需要明确记录：当前全部业务 C 文件通过主机 GCC 语法检查，但没有本机 Keil 完整构建证据，没有仓库内 AXF/HEX，也没有完整的编码器、PID 和巡线硬件验收记录。

## 7. 验证方案

实施完成后执行以下验证：

1. 确认 `CODEREADME.md` 已删除且 `STATE.md` 存在。
2. 检查 `STATE.md` 必需章节、占位词和内部状态矛盾。
3. 检查 `AGENTS.md` 的作用范围和同步规则。
4. 在临时 Git 仓库中验证预提交 hook：
   - 只提交普通文档时允许通过。
   - 提交受监控代码但不提交 `STATE.md` 时必须拒绝。
   - 同时提交代码和 `STATE.md` 时必须通过。
5. 执行设置脚本并确认当前仓库的 `core.hooksPath` 等于 `.githooks`。
6. 检查 Git 暂存范围，只提交本次设计规定的文件，不纳入用户的其他未跟踪文件。

## 8. 后续维护

`STATE.md` 描述“现在是什么”，不写成长篇代码教程。设计意图放入规格文档，具体开发步骤放入实施计划，测试细节放入阶段测试记录。当信息失效时直接更新或删除旧状态，依靠 Git 历史追溯过去，避免再次形成一份不断追加但不校正的过时说明。
