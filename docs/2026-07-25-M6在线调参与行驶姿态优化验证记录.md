## 已实现范围

### 参数与协议

- `ControlParams_t` 公开 35 个键，按 wheel、heading、line、remote 分组；维护编译默认、活动、暂存、revision、source 和 dirty 状态。
- 所有浮点输入先做有限值检查，再做字段范围和组合关系校验。普通 `apply` 仅允许无故障 `IDLE`；轮速诊断仅允许 Kp/Ki/目标在 5 ms 边界提交，并重置相应 PI 和统计窗口。
- 新事务格式为 `:<id>,...`，ID 范围 1–65535，正文最多 58 字节，连同 CR/LF 后不超过 60 字节。保留全部单字符命令；`S` 和空格在任意解析状态仍由 UART RX ISR 抢占急停。

### 掉电参数存储

- 普通应用区上限缩至 `0x0001F800`；A/B 参数扇区分别为 `0x0001F800–0x0001FBFF` 和 `0x0001FC00–0x0001FFFF`。
- V1 记录固定包含 magic、schema、length、generation、parameter revision、显式 payload、CRC32 和最后写入的 commit marker。
- 启动选择有效且 generation 最新的记录；两份无效或 schema 不认识时使用编译默认值并报告 `DEGRADED`，不锁存运动故障。
- 擦写核心位于 `.ramfunc`；每个 Flash 命令前重新解除对应保护组，RAM 内轮询期间喂 WWDT，读回校验后重新保护 A/B 扇区。目标 MAP 校验还禁止 RAM 写入器向 Flash 代码发出依赖。

### 控制与可观测性

- 轮速：运行期 PI/滤波/加减速/jerk/每轮 `kS+kV·v`，反向过零，目标硬限幅 ±700 mm/s；快照增加目标、斜坡、原始/滤波速度、误差、P/I/前馈、PWM、dt、编码器 delta 和饱和持续时间。
- 航向：解码 JY61P `0x52` 角速度；100 ms 内使用直接角速度，超时回退角度差分。校零要求角速度≤3°/s、跨度≤1°、标准差≤0.35°；近目标转向支持 smoothstep 连续减速；遥控直行航向保持启用时声明陀螺 Safety 依赖。
- 巡线：输出 active mask/count/cluster，识别空、全黑、多簇和异常宽线；位置/导数独立滤波，启动和重捕获清除 D 状态；支持动态基速、弯道降速、修正限幅/变化率和最小内轮速度。
- M6 遥测：20 ms 任务只复制固定大小整数快照到环形队列，后台整行非阻塞发送 CSV；队列和 UART 丢包进入计数和主机硬失败判定。

### 主机工具

- `scripts/m6_tune.py` 支持串口自动发现、固件/schema 核对、get/set/apply/revert/defaults/load/save、记录、评分、急停和候选回滚。
- 轮速自动搜索最多三轮、每次只改一个参数族；普通候选至少改善 5%，前馈至少改善 10%并满足四个速度点证据才接受。故障、失线、持续饱和、漏期或丢包立即停止并回滚。
- `scripts/flash.ps1` 固定走 Keil/CMSIS-DAP SWD，检查探针序列、工程、构建新鲜度、退出码、`Verify OK` 和运行中固件身份。首次命令行下载失败仅原命令重试一次，第二次失败停止并要求人工下载，不切换 GUI/BSL/配置变体。

## 下载尝试、根因与防复发

首次预检时探针尚未枚举，脚本在下载命令前停止。连接恢复后，Windows 枚举结果为：

- `Horco CMSIS-DAP v2`；
- USB 复合父设备序列号 `4041840e`；
- USB 串行设备 `COM10`。

旧预检错误地要求 Horco 名称和序列号出现在同一个 PnP 节点上，无法识别复合设备的父子拓扑。脚本已改为严格验证“序列号父设备 → Horco DAP 子设备”关系，并加入对应主机测试。

随后只调用了一次正式脚本；其既定重试策略执行了两次完全相同的 Keil 下载命令。两次均失败，最终日志 `keil/flash-20260725-133114.log` 为：

```text

Internal DLL Error
Error: Flash Download failed  -  Target DLL has been cancelled
```

没有 `Verify OK`，没有 UART 固件身份，也没有证据表明 M6 固件已经运行。按照仓库的一次原样重试上限，本轮不得再进行第三次命令行下载。

根因边界已经收敛：

- 下载脚本按自身位置选择了隔离工作树中的 M6 工程；这是包含新固件的正确源码/构建目录。
- 该工作树当时没有 `keil/empty_LP_MSPM0G3507_nortos_keil.uvoptx`。此文件被 Git 忽略，不会随 worktree 自动复制。
- 主目录 `.uvoptx` 已保存 `Use Target`、`CMSIS_AGDI.dll`、Horco `4041840e`、SWD 1 MHz、Flash sequence 和 `MSPM0G1X0X_G3X0X_MAIN_128KB.FLM`，但主目录工程仍是旧主线固件，不能直接用于下载 M6。
- `UV4.exe -f` 本身就是 Keil 的 Flash 下载参数；`-d` 会启动调试会话，不是本问题的修复。

因此用户关于“选错了先前配置好的工程/未选择 Debug 选项”的判断成立。现在 `scripts/flash.ps1` 会在任何擦写命令前强制验证相邻 `.uvoptx` 中的当前 target、Use Target、CMSIS-AGDI、Horco 名称/序列号、SWD 1 MHz、Flash sequence 和 128 KB Flash 算法；缺失或不匹配会直接停止。

本轮没有执行第三次命令行下载，用户按以下路径完成了人工恢复：

1. 架空车轮并保持车辆与 DAP 供电稳定，不进入 BSL。

## 首次 160 mm/s 基线故障与修复

用户确认双轮架空、周围无物且电机电源开启后，旧固件以默认参数启动双轮 160 mm/s，并开启 20 ms M6 遥测。原始失败记录保存在：

- `docs/m6-data/2026-07-25/baseline-160-both-r1.csv`
- `docs/m6-data/2026-07-25/baseline-160-both-r1.json`

CSV 在 `430900 ms` 开始运动，最后有效行为 `431000 ms`：ramp 69/69 mm/s、PWM 47/48、encoder delta 0/0，此前 `dt_us=5000`，故障、任务漏期和 UART/遥测丢包均为 0。随后主机收到一条只有 35 列的截断 M6 行并按安全策略急停。复位后：

- `time_ms` 从约 431 秒回到启动早期；
- 参数 revision 从运行期 2 回到默认 1；
- Safety 故障为 `0x21`，其中 `0x20` 是启动时根据 reset cause 锁存的 WWDT 复位，`0x01` 是主机在畸形行后发送的急停。

因此 35/42 列不是固件和主机 schema 不一致，而是 WWDT 在物理发送中途复位后留下的半行。

关闭 M6 遥测后，用相同双轮 160 mm/s 做对照，动作完整运行 5 秒并正常减速停止：共收到 55 条 M3 行，没有复位或调度漏期；最终左右轮平均绝对误差为 2.52%/3.64%，sign changes 为 2/6。对照监控器在收到正常 `M3 RESULT` 后仍等待周期 M3 行，误发了一次急停；该急停发生在电机已经制动之后，随后已清除并恢复 IDLE，不影响“无 M6 遥测时动作本身完整结束”的结论。

根因链为：

1. 原主循环在关键周期任务之前执行 42 字段 `snprintf`；
2. 双轮诊断每 100 ms 又格式化并输出旧 M3 CSV；
3. TX 背压时旧实现会在每次主循环对同一样本重复完整格式化；
4. 一次关键任务漏期会跳过本次 20 ms 喂狗，使相邻喂狗机会变为约 40 ms，超过约 31 ms WWDT。

修复版 `M6-runtime-20260725-r2`：

- M6 logging 开启时抑制重复的 M3/M4/M5 周期 CSV，但保留控制统计与最终结果；
- 把 `M6Telemetry_Service()` 移到 5/10/20/100 ms 周期任务之后；
- 为已格式化行增加静态 pending 缓存，TX 背压时只重试原子入队，不再重复 `snprintf`；
- 新增测试证明连续拒收时每个样本只格式化一次，并保持旧 CSV 在 M6 关闭时兼容。

`r2` 构建时已经通过 78/78 主机测试、Keil 0 error/0 warning 和镜像边界检查；随后正式脚本下载与身份核对成功。

### r2 复测与 r3 最终软件修复

在继续保持双轮架空、周围无物且电机电源开启的条件下，`r2` 以相同双轮 160 mm/s、20 ms M6 遥测运行。原始记录保存在：

- `docs/m6-data/2026-07-25/baseline-160-both-r2.csv`
- `docs/m6-data/2026-07-25/baseline-160-both-r2.json`

主机取得 206 个完整样本、持续 4100 ms，运行前段无故障、任务漏期、UART/遥测丢包或持续饱和；最后完整样本时间为 `27220 ms`。随后收到 29 列截断行并急停，目标复位到 revision 1 默认值，Safety 再次为 `0x21`，确认仍是 WWDT 复位。评分文件记录上升时间 3840 ms、超调 15%、稳态误差 6.27%、误差过零 9 次；因 `malformed_telemetry` 属于硬失败，这些性能数值不作为通过结论。

`r2` 将复位从启动约 0.1 s 延后到约 4.1 s，说明调度顺序、旧 CSV 抑制和背压缓存有效降低了负载，但并非全部根因。115200 波特率下平均数据量约占链路一半，证据更符合 32 MHz 目标上每 20 ms 执行一次 42 字段通用 `snprintf` 的偶发长尾，使一次健康窗口失败、相邻喂狗间隔达到约 40 ms并越过约 31 ms WWDT。

第二个也是最后一个有证据支撑的软件修复 `M6-runtime-20260725-r3`：

- 删除遥测后台对通用 `snprintf` 的依赖，改用固定容量、逐字段的有界整数 CSV 编码器；
- 保留已格式化 pending 行与整行原子入队，缓冲不足时不重复编码；
- 显式覆盖 `INT32_MIN`、`UINT32_MAX`、41 个逗号、CRLF 和背压恢复测试；
- 未放宽 WWDT、未增加旁路喂狗，也未改变控制周期。

`r3` 已通过 78/78 主机测试；Keil ARMCLANG 6.22 全量 Rebuild 为 0 error、0 warning，`Code=38756, RO-data=7628, RW-data=8, ZI-data=23432`，AXF 489764 B、HEX 130535 B，最高普通字节 `0x0000B537`。本记录此刻尚无 `r3` 上板结论；若相同复测仍失败，不再进行第三次软件试修，下一步必须测量目标任务执行时间、GROUP1 IRQ 频率与复位前 breadcrumb。
