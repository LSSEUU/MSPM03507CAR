# M2 调度与安全验证记录

验证日期：2026-07-22

## 1. 完成范围

本次实现对应总体 spec 的 M2“调度与安全”：

- 32 MHz 下的 1 ms SysTick 单调时基；ISR 只更新时间和释放任务。
- 5/10/20/100 ms 协作式周期调度、待运行位、完成计数和漏期计数。
- `BOOT → SELF_TEST → IDLE → RUN` 与任意运行态进入 `FAULT` 的系统状态机。
- 串口中断级急停、传感器超时、动作超时、调度漏期和 WWDT 复位故障位。
- 故障锁存首发/末发时间、请求/实际 PWM 和动作截止时间；清故障只返回 `IDLE`。
- 安全层是运行期唯一 `Motor_SetPWM()` 调用方；诊断电机测试也不能绕过。
- UART0 RX/TX 环形缓冲、异步灰度扫描、OLED 分页面刷新和非阻塞诊断动作状态机。
- WWDT0 约 31 ms；每 20 ms 仅在 5/10/20 ms 关键任务全部按期完成时喂狗。

当前 M2 不包含 M3 的轮速估计、堵转判断和速度 PI，也不包含 M4/M5 的航向与循迹控制。

## 3. 故障响应设计上界

| 故障 | 检测/裁决路径 | 软件设计上界 |
|---|---|---|
| UART `S` / 空格急停 | UART0 RX ISR → `Safety_EmergencyStop()` → `Motor_Stop()` | 不等待周期任务；ISR 路径 |
| 动作超时 | 5 ms 安全任务检查截止时间 | 截止后 5 ms 内 |
| 必需传感器超时 | 5 ms 安全任务检查时间戳 | 超时阈值后 5 ms 内 |
| 周期任务漏期 | 1 ms ISR 置漏期位，主循环锁存调度故障并制动 | 正常可调度时约 1 ms；若 CPU 卡死则由 WWDT 处理 |
| CPU/主循环卡死 | WWDT0，LFCLK 标称 32.768 kHz、2^10 周期 | 标称约 31 ms 后复位 |

软件结构给出的上界均小于 spec 的 100 ms 目标，但本次没有测量 MCU 引脚/PWM 的实物响应时间。

## 4. 待上板故障注入

下载本版 HEX 后需要在车轮架空、急停输入随时可用的条件下复核：

1. `v` 确认周期计数增长且 `miss=0`，系统在自检后进入 `IDLE`。
2. `m`、`A` 启动电机测试；每一相确认 `S`/空格立即制动并进入 `FAULT`。
3. 在测试动作中人为停止动作状态机或注入短截止时间，确认 `ACTION_TIMEOUT`。
4. 运行声明依赖 JY61P/灰度的测试动作，断开对应传感器并记录 PWM 归零时间。
5. 用受控测试固件停止喂狗，记录复位原因 `WWDT0` 和 PWM 归零时间。
6. `x` 清故障后确认只回到 `IDLE`，电机不会自动恢复先前 PWM。

## 5. 2026-07-22 串口台架实测

条件：实车车轮悬空，UART0 使用 CH340 COM5、115200 8N1。测试通过 Windows 串口接口直接发送单字符命令并保存返回内容。

已通过项目：

- 清故障后持续保持 `state=IDLE`、`faults=0`，5/10/20/100 ms 任务计数按约 20:10:5:1 增长，`miss=0/0/0/0`。
- JY61P 有效帧持续增长，抽样值 yaw=-0.58、pitch=17.89、roll=-174.07，checksum=0、frame=0。
- 灰度异步扫描返回 `[312,310,63,64,69,69,72,71]`，span=249、errors=0。
- UART 统计 tx_drop=0、rx_drop=0、format=0。
- `m`/`A` 动作中发送 `S` 后回报 `Motor test aborted by safety fault`；随后 `state=FAULT`、`faults=0x00000001`、`pwm=0,0`，调度无漏期。输入 `x` 后只返回 `IDLE`。
- 完整四相电机测试通过：dEdgeA=1539、dEdgeB=1346；动作结束后 `state=IDLE`、故障为零、PWM 为零。

阻塞缺陷：

- 发送 `o` 后先收到 `OLED pattern sent`，随后 MCU 发生 WWDT0 复位。
- 重启自检显示 `faults=0x00000020`，调度计数从零重新开始；清故障后系统可恢复 `IDLE`。
- 本地手册确认 WWDT0 使用 32 kHz LFCLK，当前 `/1 + 2^10` 配置周期为 31.25 ms。反汇编确认 OLED 仍通过软件 I2C 写整页 128 字节；高概率原因是一次页面刷新占用跨过关键任务期限，健康门控停止喂狗后复位。

本次没有示波器测量 UART 急停到 PWM 归零的物理延迟，也没有执行动作/传感器超时注入。结论为“M2 串口台架部分通过，OLED 运行期刷新缺陷阻塞硬件验收”。

## 6. OLED 运行期刷新修复记录

第一次修复将每个运行期刷新事务由 128 字节整页降为 16 字节。固件下载后通过 COM5 发送 `o`，串口先返回新的 `OLED refresh queued` 提示，随后仍重新打印启动横幅并锁存 `faults=0x00000020`。复位前调度无 miss，说明复位发生在首个软件 I²C 事务执行途中，而不是整页完成后由健康门控延迟触发。

第二次修复将刷新改为后台字节状态机：页、列低位、列高位命令分三个主循环步骤发送，数据阶段每个主循环只发送一个字节包；5/10/20/100 ms 关键任务可在包之间运行。新增静态回归保护该边界，主机 16 项测试通过，Keil 构建尺寸见第 2 节。

命令行下载链路先后出现 `Erase Failed` 和 `Debug access failed`；用户随后完成下载并重新启动目标。第二次实车复验的基线为 `state=IDLE`、`faults=0`、`release=14730/7365/3682/736`、`miss=0/0/0/0`。发送 `o` 后收到排队提示，12 秒后的状态仍为 `IDLE`、`faults=0`，调度计数连续增长到 `17669/8834/4417/883`，通信丢包为零且 OLED 样本计数由 1 增至 2；但同一批串口尾部随后出现新的启动横幅。追加读取确认 `faults=0x00000020` 且调度计数已降为 `4142/2071/1035/207`，之后又出现启动横幅和 `release=160/80/40/8`，证明 WWDT0 复位仍存在。

由于 16 字节分片与后台单字节状态机两次实现尝试都未解决同一问题，按仓库问题调查规则停止继续尝试分片变体或放宽看门狗。现有证据只能确定触发条件与 OLED 运行期刷新相关，但单次事务阻塞不是充分解释。下一诊断决策应是用 GPIO/逻辑分析仪同时观察喂狗标记和 SCL，测出最后一次喂狗到复位的真实间隔；没有仪器时，使用受控诊断固件记录 OLED 服务前后时间、WWDT 计数/状态和健康窗口，并单独验证复位原因寄存器。形成该证据前不进入 M3。
